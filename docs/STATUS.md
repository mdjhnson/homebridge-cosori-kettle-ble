## Open issues (priority order)

1. **The link drops, on the USB adapter too. Mitigated (it now recovers), but the margin is still thin.** On the onboard radio the link dropped twice during heating (history below) and the Pi then couldn't hear the kettle at all, even while a Mac next to the Pi heard it advertising at about -63 dBm. A TP-Link UB500 (RTL8761BU) on a USB 2.0 port improved things but didn't fix them:
   - **Good:** first connect in 4.4 s (10–40 s before). One full heat-and-hold cycle (Green Tea from the kettle's button, 20:10–20:45) ran with no drop, 0 HCI errors, and the kettle never advertised (so it never disconnected).
   - **Bad, after the 21:03 reboot** (btmon on the UB500, now `hci0`, capture from about 21:08): plugin-level drops at 21:18:54, 21:22:25, 21:30:20 (all idle, about 138 °F), 21:41:50 (idle, just after a heat started and stopped at the kettle), 21:45:03 (**heating**, about 176 °F), 21:46:22 (holding). That's 6 in about 28 min, plus two more HCI disconnects during reconnect attempts. **Every one is Disconnect Complete 0x08 Connection Timeout.** Connection parameters: 45 ms interval, latency 0, 6 s supervision timeout (the kettle requests it via L2CAP and we accept), so each drop is at least 6 s of total silence from the kettle.
   - **Not caused by polling:** before drop 1 the poll write got no response. Before drop 2 the write was acknowledged at the link layer, then silence. Before drop 3 the silence began about 1.3 s after the previous reply, before any write.
   - **Recovery now works** (first time seen after a real drop): usually LE connect plus hello ACK about 4 s after the disconnect. Once (21:45:03) a reconnect failed on "GATT service discovery timed out after 30000 ms" and it took about 60 s. The log shows only "Lost connection…; reconnecting". Quick reconnects log at debug level, so a recovered drop looks the same as an unrecovered one.
   - **Margin:** the kettle's advertising RSSI on the UB500 was -80 to -84 dBm at every reconnect. The adapter is already on a USB extension cable at the back of the furniture the Pi sits in, just outside the kitchen, about 10 ft from the kettle. **That's the closest it can ever be**, so a better placement isn't an option. (`lsusb` shows the logical port, not the extension cable; an earlier note here wrongly said it had no extension.) A kettle-side radio pause isn't ruled out: some drops were idle, one was during heating.
   - **What a drop costs today:** HomeKit keeps answering from cached status (considered current for 90 s), and a command sent while the link has been down less than 15 s waits and runs after the reconnect. A command that a drop cuts off (sent in the few seconds of silence before the disconnect is noticed) is sent once more after the reconnect, if that comes within 30 s, and commands run one at a time in the order they were issued (branch `fix/resend-after-drop`; before it, such a command failed and wasn't retried). A typical drop (6 s of silence plus about 4 s to reconnect) is a few seconds of delay, not a failure. Outages longer than 15 s (like the 60 s one, or 19.9 s and 31.5 s on 2026-09-26) make taps show "No Response".

   **Plan (agreed with the user 2026-09-24):** treat drops as a normal operating condition (other users will have marginal links too) and make the plugin handle them well, rather than chasing range.
   1. **Reconnect logging** (done in code): an info line when a reconnect succeeds after a drop ("Reconnected to the kettle after 4.1 s (1 attempt, …)"), and elapsed-time warnings while the link stays down (1, 5, 15, 30 min, then hourly), replacing the attempt-count thresholds. Deploy with the user's OK (Kettle child bridge restart only).
   2. **Measure the real impact** during normal use and the Checkpoint C tests: drops per hour, reconnect times, and whether any HomeKit tap actually fails or shows "No Response". btmon keeps recording the reason codes.
   3. **Fix slow reconnects** if they recur (the 60 s case was a GATT discovery timeout after a connect). (A timed-out connect was already cancelled: the transport calls `Device1.Disconnect` on failure, see FUTURE-WORK §3.)
   4. **Decide from the numbers:** if drops stay invisible in HomeKit, accept them and document it for users. If they cause visible failures, run the diagnostic below and consider an adapter with an external antenna.
   - **Optional diagnostic, only if step 4 needs it:** put the kettle next to the adapter for about 30 min (idle, no heating needed). Drops continue up close → kettle-side or interference, and no adapter or antenna will help. Drops stop → signal margin, and a USB Bluetooth adapter with an external antenna (about $15–20) could help at 10 ft.
   - btmon is not running (stopped 2026-09-25). For reason codes, start it again (`docs/local/argonpi.md`). A capture spans reconnects, so it contains hello frames with the key: print only events and kettle notifications.

5. **Known, harmless: `gyp ERR!` for `usocket` in npm install logs.** **Fixed in code (branch `feat/bluez-transport`, FUTURE-WORK §3b):** `node-ble` is replaced, so `usocket` is gone from the dependency tree; ships in the next release. History: Seen on the Pi (Node 24.20.0) while installing another plugin through the Homebridge UI. npm re-runs install scripts across `/homebridge`, and `usocket@0.3.0` (an optional dependency, via node-ble ~1.13.0 → dbus-next 0.10.2) pins node-gyp ^7.1.2, which can't build on Node 24. It isn't a missing toolchain: the container has python3, make and g++. npm skips the optional dep and the install succeeds. `usocket` has been absent from the plugin's `node_modules` on the Pi since the first tarball install, so the plugin has always run without it. `dbus-next/lib/connection.js` wraps `require('usocket')` for `unix:path=` addresses in a try/catch and falls back to `net.createConnection`. That only loses Unix-FD passing (node-ble doesn't use AcquireNotify/AcquireWrite) and `unix:abstract=` addresses (not used for the system bus). The cost is a scary log line and a failed native build on every plugin install. An `overrides` entry in our `package.json` wouldn't help: overrides don't apply to consumer installs. **Decision: leave it, documented in README Troubleshooting.** Don't add an `overrides` entry to the shared `/homebridge/package.json` on the Pi. See FUTURE-WORK §3 for the longer-term option.
